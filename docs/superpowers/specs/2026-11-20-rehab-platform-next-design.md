# 康复训练辅助平台重建方案

日期 2026-11-20 · 用户已确认开工，优先交付真实摄像头跟练

## 目标

在 `rehab-platform-next/` 新建《融合视觉姿态感知与动作质量评估的智能康复训练辅助平台》。以数据库课程答辩为交付场景，训练者和指导者应能用浏览器完成一轮训练，并在页面上看到保存后的记录和复核结果。以 `rehab-platform/` 为功能、参考文献、模型来源和测试案例的来源。新版使用独立端口 `8081`、独立数据目录及数据库名，首版用全新演示库启动。旧版训练数据导入另立任务。

### 方案选择

用户已选定独立重建。保留原项目并增量修复可以更快复用旧数据和接口，但需要围绕已有会话、报告状态逐项兼容。独立重建让页面、API 和数据关系按同一条训练流程设计，也能并排运行验证。技术栈由本方案建议沿用 Vue 与 Java 的方向，采用 Vue 3、Vite、Element Plus、ECharts、Java 17、Spring Boot 3.x、MyBatis、Flyway 和 MySQL 8。H2 提供独立的本机演示和测试配置。当前本机检测到 Java 8，实施阶段将为新版配置项目内的 Java 17 运行环境，旧版使用自己的现有启动方式。MySQL 另行做实例验收。

训练流程面向由指导者配置个体目标、训练者记录动作和指导者人工复核的场景。第一版支持肩前屈、肩外展、肘屈伸。姿态使用 MediaPipe 官方权重和浏览器本地推理。浏览器运行 TypeScript 规则，服务端 Java 复算，双方使用同一份规则配置和跨语言回归夹具。阶段、计数和事件类型必须一致，角度差容许 0.1° 以内。Python 用于后续实验和模型训练。原始影像留在浏览器，只提交关键点。

## 第一阶段交付

| 页面 | 可操作功能与结果 |
| --- | --- |
| 管理员工作台 | 创建、启停训练者及指导者账号，为训练者分配一名当前指导者。启停影响登录和现有会话，历史业务记录保持可查。初始化提供管理员、两组互不相属的指导关系，用于场景验收。 |
| 指导者工作台 | 查看负责学员、待复核报告和近期计划。为学员登记或更新训练侧、观察条件及基线备注，旧基线可查。 |
| 动作库 | 可查看三动作的动作说明、建议机位、参考图示链接、适用条件及规则版本。第一阶段用已核对的 AAOS / ASES 资料，本地有授权的真人视频单独补充。 |
| 计划编辑与发布 | 选学员、动作、侧别、日期、组次、休息和记录方式。目标比较模式由指导者明确设定幅度、节奏和保持，发布前可预览。已发布计划固定，调整以新版本和变更说明发布。 |
| 训练者工作台 | 查看可执行计划、进行中的训练、已完成报告和指导反馈。在计划详情进入跟练。默认仅观察，也可按计划做目标比较。 |
| 跟练 | 先预览，明确开始后才创建会话。按组采集，显示骨架、投影角度、阶段、计数及采集质量。可暂停、恢复、结束当前组、结束本次训练、取消。采集不足或无完整循环时允许取消，也允许按采集情况生成仅有观察结论的报告。 |
| 报告与回放 | 显示已完成及未完成的组、完整循环、实际使用的目标、缺失观测、分项判断和参考资料。点击事件时间打开对应关键点片段。提供 CSV 和支持打印为 PDF 的页面。 |
| 人工复核 | 指导者对每条待审事件确认或驳回，可留总体意见。逐条处理后通过独立按钮完成复核。无事件的报告可直接填写总体意见后完成。训练者可看到结果与说明。 |
| 历史统计 | 按日期、动作、侧别和来源筛选训练记录。展示计划完成数量、状态分布及重复次数。角度趋势限可比较记录，使用相同动作、侧别、机位配置和规则版本。 |

页面采用按角色显示的工作台。训练时将摄像头与反馈放在同一视区，“暂停”“结束并保存”“取消训练”始终可达。报告首屏显示训练结果和复核状态，问题与回放沿同一时间轴对应。

## 数据与状态设计

| 业务 | 主要实体与约束 |
| --- | --- |
| 账号与指导 | `user_account`、`login_session`、`coach_assignment`。账号密码哈希，登录会话可撤销。每学员一个当前指导者，分配变更留历史。指导者权限以当前负责学员为准，调整权限后历史作者和记录保留。 |
| 档案 | `trainee_profile`、`baseline_record`。每学员一份档案，基线追加留痕，计划版本可引用一条基线。 |
| 动作 | `exercise`、`exercise_version`。固定代码，版本内记录动作说明、参考资料、建议机位、工程参数与版本号。 |
| 计划 | `training_plan`、`plan_version`、`plan_item`。同一计划的版本号唯一。计划明细固定动作版本、侧别及个体目标。版本化的长文本说明可存于计划版本表。 |
| 会话与采集 | `training_session`、`session_set`、`capture_chunk`。固定计划版本和输入来源，每组每个采集批次有唯一编号。保存带时间戳的关键点块及版本信息。 |
| 分析与复核 | `repetition_result`、`issue_event`、`training_report`、`event_review`、`report_review`。每组动作序号唯一。事件关联循环或采集时间窗。报告与会话一对一。人工判断追加历史，并明确当前结论。 |

计划版本状态为 `DRAFT → PUBLISHED → SUPERSEDED`。只有当前已发布版本可开新会话，已经开始的训练继续引用原版本。

一个会话执行一个计划版本，可按计划顺序执行多个动作和组。计划日期用于安排和展示，当前发布版本允许提前执行及补做。同一训练者最多存在一个进行中的会话。完成或取消后可以重新训练。计划仅在至少一个会话达到所有动作计划组数及每组次数时计为完成，同一计划只计一次。从报告调整计划时，预填原计划明细并创建同一计划的新草稿版本，记录来源报告和变更说明，指导者可编辑再发布。

训练会话状态为 `IN_PROGRESS → COMPLETED` 或 `IN_PROGRESS → CANCELLED`。暂停为采集行为，恢复沿用同一会话。结束当前组后记录结束时间及实际数据。该组完整循环仍计入报告，只有达到计划次数的组才计为完成。结束会话时允许保存部分观察，零可靠帧的报告明确标记数据不足。取消保留会话头和取消时间，可在历史状态筛选中查看。临时帧随取消清理。

恢复范围为同一账号与浏览器内的刷新和短时断网。每个准备上传的批次先写入 IndexedDB，收到服务端确认后方可删除本地副本。恢复时按序重试未确认批次，仍在内存且来不及写入的帧在时间轴上显示为采集断点。存储不可用或上传失败时明确提示，并允许重试或取消。正常结束等待待上传批次全部确认，再提交最后确认的批次序号，服务端核对组内批次连续性后复算。

报告复核状态为 `PENDING → IN_REVIEW → FINALIZED`，与会话完成状态独立。添加意见只把报告置为进行中。全部待审事件都有确认或驳回且已填写总体意见后，才能最终完成。最终完成后可通过追加反馈保留补充意见，原复核结论保持可追溯。

训练数据以毫秒整数记录会话相对时间，页面转换为秒展示。上传批次绑定组号和单调递增的帧时间。重复上传同编号同内容返回原确认，异内容返回冲突。上传、完成和取消在服务端按会话串行变更。分析使用固定输入批次集合，完成事务同时写报告、组汇总、循环和事件，重复完成请求返回已保存报告。无可靠角度、未评价或不适用的数值和分项写 `NULL`，并保存导致缺失的原因。

## 接口与数据流

接口统一从 `/api/v1` 开始。账号、档案、计划、会话、报告和统计使用各自的路由与数据类型。所有写接口验证当前登录身份和访问范围。演示与真人记录保存独立来源，合成测试夹具只进入测试数据库。用于页面演示的固定关键点回放若后续加入，必须醒目标注来源，并与摄像头记录分开统计。

| 场景 | 接口草案 |
| --- | --- |
| 管理账号与档案 | `POST /accounts`、`PATCH /accounts/{id}`、`PUT /trainees/{id}/coach`、`PUT /trainees/{id}/profile`、`POST /trainees/{id}/baselines` |
| 发布及后续版本 | `POST /plans`、`POST /plans/{id}/versions`、`PUT /plan-versions/{id}`、`POST /plan-versions/{id}/publish` |
| 训练采集 | `POST /sessions`、`GET /sessions/{id}`、`PUT /sessions/{id}/sets/{setId}/chunks/{seq}`、`POST /sessions/{id}/sets/{setId}/finish`、`POST /sessions/{id}/finish`、`POST /sessions/{id}/cancel` |
| 报告与复核 | `GET /reports/{id}`、`GET /reports/{id}/evidence?fromMs=&toMs=`、`POST /reports/{id}/events/{eventId}/reviews`、`POST /reports/{id}/reviews`、`POST /reports/{id}/finalize-review` |
| 历史与导出 | `GET /reports`、`GET /reports/{id}/export.csv`、`GET /statistics/training` |

浏览器获取摄像头视频与姿态模型，缓存待上传关键点块，并显示即时反馈。Java 读取计划和动作版本，对上传的带时间序列关键点做几何角度、可见性门控、起始校准、动作循环分段和分项判定。可见性不足时暂停评价，长间断后重新校准。报告定位按时间窗按需读取关键点。训练者自报疼痛信息可选，作为观察事实随报告保存。幅度报告说明是指定机位的图像平面投影，工程阈值和个体目标各自附来源。

首版沿用旧版已具备合成测试的规则语义作为基线，重新实现并用夹具核对。肩前屈用训练侧侧面机位，肩外展用正面机位，均量髋、肩、肘的投影夹角。肘屈伸用训练侧侧面机位，以 180° 减去肩、肘、腕的夹角。每动作独立校准起始姿势，检测抬起或屈曲并稳定回到起始位置后计一次。规则初值参考旧版，按动作和版本配置并在真人验收后调整。仅观察时保留循环与角度，目标模式比较峰值区间、完整循环耗时和目标区间连续保持。每个不满足目标的分项生成一条待审事件，明显的躯干投影变化单列观察事件。遮挡、多人及入镜不足作为采集质量记录和时间轴标记。数据不足时不生成动作质量判断。

## 验收与推进顺序

1. 基础业务。启动新服务，管理员创建训练者并绑定指导者，指导者保存档案和基线，完成三动作计划发布。训练者只能看到自己的计划，第二组账号验证越权拦截。
2. 采集和异常路径。在浏览器用摄像头完成一组动作，检查预览、计数、暂停、恢复、报告和事件回放。验证拒绝权限后可重试、已开始但无帧可取消、刷新或连接中断后可恢复、重复上传不会重复计数。
3. 人工复核和版本。指导者逐条决策，完成报告复核，从报告建立后续计划。训练者能查看已完成的复核，以及旧报告所用的历史计划。
4. 数据库和交付。验证 H2 的全流程、重启保留数据、真实 MySQL 的从空库迁移与多表事务、重复提交和权限。保留脚本、浏览器测试结果及数据库关系图，写清验证数据来源。真人验收至少对三动作各手工对照一组，记录侧别、机位、人工计数、系统计数和失败原因。样本范围仅支持演示级结论。

每阶段按 Superpowers 实施与验证，先写能验证失败路径的测试，再实现并回归。交付时分别记录自动化通过、浏览器实际完成、真人验证和待完成项。后续实验需按训练者或录制场次切分独立样本，单独报告模型和规则误差。

第二阶段加入花朵手势、授权真人示范和更丰富的训练趋势。PyTorch 质量模型建立在标注与规则对照之上。BNO055 作为独立实验，依次验证双传感器数据、佩戴标定及参考测量，再接入业务。开发主流程使用 Superpowers。跨版本出现需求变更时可补 OpenSpec，业务术语或接口边界模糊时可补 Matt Pocock 的领域建模或代码设计技能。
